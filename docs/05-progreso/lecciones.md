## Lecciones Aprendidas

Documento para registrar "qué salió bien, qué salió mal y por qué" a lo largo de la transición.

Se completa al final de cada fase y cuando el proyecto termine.

---

### Formato

Cada lección sigue:

```markdown
### Lección: [Título]

**Fase**: N (0-5)

**Contexto**: Qué pasó

**Hallazgo**: Qué aprendimos

**Recomendación**: Cómo aplicarlo en el futuro

**Aplicable a**: Otros proyectos similares? (sí/no)

**Responsable de documentar**: @usuario

**Fecha**: YYYY-MM-DD
```

---

### Ejemplo de Lección (Template)

### Lección: Importancia de Validar Datos Antes de Migrar

**Fase**: 2 (Deuda Técnica)

**Contexto**: 
Al migrar el dataset de transporte de GeoJSON a GPKG, descubrimos que 10% de los registros tenían coordenadas duplicadas. Esto no fue detectado en la inspección inicial porque los archivos eran pequeños (~5 MB).

**Hallazgo**:
- Ojos humanos no detectan duplicados en archivos de tamaño mediano
- `ogrinfo` sin flags específicos no reporta duplicados automáticamente
- Tests manuales en QGIS son insuficientes; necesitamos validación programática

**Recomendación**:
- Fase de "inspección de datos" siempre incluir: SQL query de `COUNT(DISTINCT geometry)` vs `COUNT(*)`
- Documentar cantidad de registros esperados ANTES de migrar
- Ejecutar tests de duplicados como parte de CI

**Aplicable a**: 
✅ Sí. Proyectos de migración de datos siempre tienen sorpresas.

**Responsable de documentar**: @usuario

**Fecha**: 2027-01-25

### Cómo Usar Este Documento

1. **Después de cada fase**: convocar retrospectiva, documentar lecciones
2. **Para onboarding**: nuevas personas leen lecciones antes de empezar
3. **Para auditoría**: este doc es evidencia de cómo aprendimos y mejoramos
4. **Para el siguiente proyecto IDE**: copiar lecciones aplicables a README nuevo

---

### Notas Generales

- Lecciones son **conocimiento acumulado**, no crítica. Tono constructivo siempre.
- Cada lección es un commit separado, no se borra (histórico es valioso)
- Si una lección se aplica y da resultado, se documenta. Si no, se marca como "deprecated"
- Archivo se entrega al cliente al final de Fase 5 como parte de "project knowledge transfer"

### Cómo Iniciar Retrospectiva

Convocatoria por email 1 semana antes del cierre de fase:

```
Subject: Retrospectiva Fase N - [Fecha]

Body:
¡Hola equipo!

En X días cerramos Fase N. Quiero invitar a todos a participar en retrospectiva.

Cuándo: [Día] [Hora] ART
Dónde: [Link a meet]
Duración: 90 min

Agenda:
1. ¿Qué salió bien? (30 min, brainstorm)
2. ¿Qué salió mal? (30 min, root cause)
3. ¿Qué mejoramos? (30 min, acciones)

Por favor traer:
- Notas de lo que trabajaste
- Issues que encontraste
- Sugerencias de mejora

Gracias,
[Líder Proyecto]
```

Después de retrospectiva, líder proyecto redacta lecciones y abre PR para review.
